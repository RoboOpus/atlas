## 结论先行

机器人系统里很多“算法不稳定”，最后并不是优化器、网络或控制器的问题，而是坐标系约定没有成为可执行契约。相机给出的点、标定得到的外参、规划器生成的末端位姿和控制器读取的机器人状态，必须回答同一个问题：**这个量在哪个坐标系中表达，它描述谁相对谁？**

本文采用 `T_ab` 表示坐标系 `{b}` 相对于 `{a}` 的位姿，同时它把在 `{b}` 中表达的齐次坐标转换到 `{a}`：

```math
p_a = T_ab p_b
```

只要团队坚持这个记号，复合关系就能像消去单位一样阅读：

```math
T_ac = T_ab T_bc
```

中间的 `b` 消去，结果是把 `{c}` 中的量变到 `{a}`。这比“先旋转还是先平移”的口头讨论更可靠。

## 齐次变换到底包含什么

三维刚体位姿由旋转 `R_ab` 和平移 `p_ab` 组成。将它们写成 4×4 齐次矩阵：

```math
T_ab = [ R_ab  p_ab ]
       [ 0 0 0    1 ]
```

其中 `p_ab` 是 `{b}` 原点在 `{a}` 中的坐标，`R_ab` 的列向量则描述 `{b}` 三根轴在 `{a}` 中的方向。所有合法刚体变换组成特殊欧氏群 `SE(3)`；两个合法变换相乘仍是合法变换，且每个变换都有逆。[S1]

齐次矩阵有三个常见角色：表示刚体配置、改变向量或坐标系的表达参考系、以及对点或坐标系施加位移。[S1] 工程代码中最危险的做法，是用同一个 `transform()` 函数完成这三种语义，却不在类型或命名中区分。

## 复合、逆与左右乘

逆变换不需要通用矩阵求逆。利用旋转矩阵正交性：

```math
T_ba = inverse(T_ab)
R_ba = transpose(R_ab)
p_ba = -transpose(R_ab) p_ab
```

左乘和右乘也不是纯粹的记号差异。一个增量变换左乘当前位姿时，增量通常在外部或空间坐标系表达；右乘时，增量通常在随物体运动的本体坐标系表达。[S1] 因此“沿 x 方向移动 10 cm”没有坐标系就不是完整指令：它可能是世界 x、基座 x、末端 x 或相机 x。

建议在接口命名中直接写出语义，例如：

- `T_world_camera`：相机坐标到世界坐标的变换。
- `T_base_ee`：末端坐标到机器人基座坐标的变换。
- `p_object_camera`：物体点在相机坐标系中的数值。
- `twist_ee_in_base`：末端速度，表达在基座坐标系中。

如果代码库使用另一种约定，例如 `T_a_b` 表示 `{a}` 到 `{b}`，也可以工作；关键不是选择哪一种，而是**只能有一种，并能由测试验证**。

## 从感知到控制的数据链

设视觉系统输出目标点 `p_object_camera`，标定给出 `T_base_camera`，规划器需要目标在基座坐标系中的位置：

```math
p_object_base = T_base_camera p_object_camera
```

若还要得到目标相对末端的坐标，并且机器人状态给出 `T_base_ee`：

```math
p_object_ee = inverse(T_base_ee) T_base_camera p_object_camera
```

这条链同时连接标定、视觉、运动学和控制。任何一个模块若混用毫米与米、左手与右手系、`camera-to-world` 与 `world-to-camera`，最终误差都会以“抓取偏一点”“轨迹突然翻转”或“控制器发散”的形式出现。

## 最小可执行检查

不要只通过可视化判断坐标变换。至少建立以下自动测试：

1. **单位变换**：`T_aa` 必须为单位阵，作用于任何点都不变。
2. **逆变换**：`T_ab T_ba` 和 `T_ba T_ab` 都应在容差内等于单位阵。
3. **闭环复合**：任意链 `T_ab T_bc T_ca` 应回到单位阵。
4. **已知点测试**：构造一个 90° 旋转加已知平移，手算一个点的结果。
5. **单位检查**：平移统一使用米，角度进入三角函数前统一使用弧度。
6. **旋转合法性**：检查 `R^T R = I` 且 `det(R) = 1`。

数值优化或网络预测的旋转可能逐渐偏离 `SO(3)`。此时应显式投影回合法旋转，或使用轴角、四元数、李代数增量等结构化参数化，而不是让错误矩阵继续进入动力学与控制。

## 常见失败模式

- **下标语义反了**：视觉库返回 `camera-from-world`，代码却按 `world-from-camera` 使用。
- **行向量与列向量混用**：公式采用左乘列向量，某个库却把点存成右乘行向量。
- **外参只存了数值，没有方向**：文件名叫 `extrinsic.json`，半年后没人知道它是哪两个坐标系之间的变换。
- **位置正确、姿态错误**：只用平移做过测试，没有验证旋转和复合顺序。
- **时间不同步**：数学上的变换链正确，但相机外参和机器人状态来自不同时间戳。
- **默认单位不一致**：CAD 用毫米，机器人驱动用米，角度日志用度，优化器用弧度。
