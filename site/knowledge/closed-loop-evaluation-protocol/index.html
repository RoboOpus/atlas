  • 闭环评测的单位应是可重放场景与事件，不只是平均成功率。
  • 离线感知指标、仿真性能和真实任务结果需要分层报告。
  • 版本、随机种子、传感器和时间模式是评测结果的一部分。

为什么只看成功率不够

机器人任务的成功率会把不同问题压成一个数字：感知丢失、规划超时、控制震荡、抓取滑移和安全停止都可能记作一次失败。两个系统即使成功率相同，风险结构也可能完全不同。

自动驾驶研究长期面对场景复杂、多主体交互、稀有危险事件和闭环误差累积。可迁移到机器人领域的核心不是道路数据本身，而是三件事：场景参数化、多传感器时空组织，以及围绕事件的切片与重放。

三层评测必须分开

  1. 离线层：在固定数据上测感知、预测或策略输出，不改变未来观测。
  2. 仿真闭环层：动作会改变后续状态，可系统扫描场景并注入扰动。
  3. 真实闭环层：包含真实摩擦、柔性、时延、磨损、人员和安全约束。

离线提升不能自动推出闭环收益，仿真收益也不能自动推出真机收益。每层都应保留自己的输入、版本和通过条件，并明确下一层新增了哪些不确定性。

场景矩阵而不是演示视频

CARLA 官方基准脚本允许组合地图、传感器和天气，并明确记录同步/异步模式、固定时间步、渲染设置、软件版本和运行硬件。[S1] 机器人评测可采用相同结构，把轴换成：

  • 对象：尺寸、质量、材质、可变形程度；
  • 环境：光照、遮挡、背景、桌面摩擦和空间拥挤度；
  • 初始状态：位姿、机器人关节状态、抓取候选与定位误差；
  • 扰动：外力、对象移动、延迟、丢帧和模型参数偏差；
  • 系统模式：同步/异步、控制频率、算力限制与安全阈值。

矩阵不必一次做满。先选择最可能改变结论的两个轴，覆盖中心条件、边界条件和一个故意困难的反例。

事件账本

每次运行至少记录：

run_id / scenario_id / software_commit / model_id
robot / tool / object / calibration_id
sensor timestamps / control timestamps / random seed
task outcome / time-to-complete / safety events
failure_stage / failure_code / first-divergence-time
raw-log URI / video URI / replay command

Waymo Open、nuScenes 与 KITTI 展示了不同形式的大规模传感器、轨迹、地图与任务评测组织。[S2][S3][S4] 对机器人最值得迁移的不是把它们的数据字段照搬，而是给场景、传感器、标注和评测版本稳定身份，使同一失败能跨模型和时间比较。

找“第一次分叉”

闭环失败分析不要只标最后结果。应定位相对于成功参考运行的第一次明显分叉：目标首次丢失、状态估计首次跳变、规划首次不可行、轨迹误差首次越界，或接触力首次异常。

第一次分叉不必等于根因，但它能缩小回放范围。随后分别做反事实替换：使用真值感知、固定规划、理想控制或重放同一动作，观察失败是否消失。这样可以避免把末端掉落简单归因于“策略不够强”。

一个可执行的最小协议

  1. 定义 12—20 个场景，覆盖对象、初态和一个扰动轴。
  2. 每个场景至少运行多个随机种子，保存所有失败而非只保存最好视频。
  3. 报告整体成功率，同时报告按场景与失败阶段切片的结果。
  4. 固定一套回归场景，在每次模型、控制器或硬件变更后重跑。
  5. 对高风险失败保存可重放包；不能重放时，至少保存同步日志、视频和配置。
  6. 将仿真与真机结果并列，明确哪些场景参数无法对齐。

不要让基准绑架研究问题

公开数据集容易测量，但机器人真实瓶颈可能不在现有标签里。若研究目标是接触安全，就应加入峰值力、滑移、碰撞和停止事件；若目标是长时任务，就应记录恢复次数、累积漂移和人工介入，而不能只沿用图像或轨迹误差。

RoboOpus 后续会把闭环评测沉淀为“场景注册表 + 运行账本 + 失败切片”。论文表格是其派生结果，原始证据和重放入口才是长期可进化的知识。
