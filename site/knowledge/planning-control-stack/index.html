先把五层对象分开

一个“把杯子放到托盘”的目标，至少会经过五层表示：

  1. 任务层决定先接近、再抓取、再抬起、最后放置。
  2. 几何路径层寻找从起始构型到目标构型的无碰撞曲线。
  3. 时间轨迹层为路径增加时间、速度和加速度约束。
  4. 反馈控制层根据实时误差计算关节力矩、速度或位置命令。
  5. 执行与安全层处理驱动器、限位、急停、通信超时和状态机。

这五层常被混成“规划控制算法”，导致接口模糊。最典型的问题是：规划器输出了一串几何路点，系统却直接把它当作可执行轨迹；或者学习策略输出末端增量，却没有说明它运行在哪个参考系、频率和约束下。

OMPL、MoveIt 2 和 ROS 2 各自在哪里

OMPL 集中实现采样式运动规划算法。它处理抽象状态空间中的规划问题，本身没有完整机器人概念；上层系统需要提供状态空间、有效性判断、碰撞检查和问题定义。[S2]

MoveIt 2 把机器人模型、规划场景、碰撞检查、约束、规划插件、时间参数化和轨迹执行连起来。其默认规划器可由 OMPL 提供，也可以通过插件接口替换。官方文档明确区分规划请求、规划结果和请求/响应适配器；典型规划结果是轨迹，而不仅是几何路径。[S3]

ROS 2 是模块之间的运行时接口层。连续传感器和状态流适合 Topic，短请求适合 Service，耗时且需要反馈、取消的目标适合 Action。[S4] 因此“执行一条机械臂轨迹”通常更像 Action，而“查询当前工具配置”更像 Service；将所有通信都塞进 Topic 会让完成、失败和取消语义变得模糊。

路径为什么不能直接执行

几何路径只规定构型的顺序，不一定包含时间。真实机器人还受关节速度、加速度、跃度、扭矩、碰撞距离和控制周期约束。时间参数化的职责，是把路径变成满足运动学约束的轨迹；轨迹优化则可能把动力学、平滑、避障和任务代价同时纳入优化。

这也解释了两个不同失败：

  • 规划失败：找不到从起点到终点的候选路径。
  • 执行失败：路径存在，但时间化、跟踪、模型误差、摩擦或通信使真实机器人偏离。

成功的仿真动画只能证明某个模型和求解配置下的执行；它不能替代真实系统上的跟踪误差和安全测试。

MPC 在哪一层

模型预测控制使用当前状态反复求解有限时域优化，只执行当前最优解的第一步，然后重新测量和优化。MIT Underactuated Robotics 将其概括为“测量—优化—执行第一步—重复”的滚动流程。[S5]

u_t = first_action(argmin trajectory_cost(x_t, u_t ... u_t+H))

MPC 将规划和反馈连接起来，但它不会自动消除模型误差、求解延迟或不可行性。系统必须明确：

  • 状态估计在什么频率更新，延迟多大；
  • 求解器在控制周期内是否稳定完成；
  • 优化不可行时使用什么安全回退；
  • 约束是软约束还是硬约束；
  • 模型与真实硬件偏差如何监测。

一条建议的软件契约

以下契约比绑定某个工具更重要：

  1. 任务输入：对象、目标关系、成功条件、允许的失败与恢复策略。
  2. 规划场景：机器人状态、环境几何、碰撞对象、时间戳和不确定性。
  3. 路径输出：构型序列、规划器、随机种子、约束和规划耗时。
  4. 轨迹输出：时间戳、位置、速度、加速度以及限制来源。
  5. 执行结果：是否完成、最大误差、停止原因、安全事件和日志链接。

每层都保留输入、输出和版本，才能定位失败属于感知、规划、时间化、控制还是硬件。

从仿真到真机的测试阶梯

推荐按风险递增，而不是一次性“上真机”：

  1. 对固定场景做离线规划，检查路径连续性和碰撞。
  2. 在仿真中加入时间参数化，验证速度与加速度限制。
  3. 用记录的真实状态回放规划和控制接口。
  4. 真机低速、无负载运行，设置保守工作空间。
  5. 加入末端执行器与负载，重新核对质心和动力学参数。
  6. 执行完整任务，同时记录计划轨迹、实际轨迹、控制误差和停止事件。

常见失败模式

  • 规划场景更新比机器人运动慢，碰撞模型使用旧状态。
  • 规划器和控制器对关节限制使用不同配置。
  • 路径有可行解，但时间参数化无法满足加速度限制。
  • 控制器名称相同，实际接口却分别是位置、速度或力矩。
  • ROS 发行版、MoveIt 分支和机器人驱动版本不匹配。
  • 只记录“成功率”，没有记录失败发生在哪一层。

RoboOpus 后续应为每个真实系统保存一张“规划控制契约卡”：机器人模型版本、规划插件、控制接口、频率、限制、安全回退和最小复现实验。它比泛泛列出算法名称更接近可用知识。
